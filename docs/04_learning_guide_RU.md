# Объяснение PC Build Planner (для защиты)

## 1. Что происходит, когда нажимаешь Create a build

1. Браузер отправляет **POST** по адресу `/builds/new` с названием, бюджетом и защитным токеном.
2. В `app.py` функция `create_build()` находит пользователя, проверяет CSRF и допустимость данных.
3. `db.py` открывает соединение SQLite.
4. SQL `INSERT INTO builds (...) VALUES (?, ?, ?)` создаёт запись в базе.
5. Сервер отправляет перенаправление **303** на страницу новой сборки; браузер выполняет GET.

Вопрос: зачем 303? Чтобы обновление страницы не повторило POST и не создало дубликат.

## 2. Как хранится база

Пять таблиц:
- `users`: пользователи и роли;
- `categories`: типы деталей;
- `components`: компоненты, цена, категория;
- `builds`: сборки и владельцы;
- `build_items`: какие детали входят в какие сборки.

Пример: сборка 7 может включать компонент 2 и компонент 5 — это две строки в `build_items` с `build_id=7`.

**Primary key (PK)** — уникальный ID записи. **Foreign key (FK)** — ссылка на ID другой таблицы. **One-to-many** — один пользователь может иметь много сборок.

## 3. Как считается стоимость

Цена каждой детали хранится в `price_cents`, например 19000 означает €190.00. Для каждой строки `build_items` цена умножается на количество. Потом всё суммируется. На странице `/builds/{id}` это `sum(...)`, а на главной/report — SQL `SUM(...)` с `JOIN`.

## 4. Почему разные технологии

**HTML/Jinja2**: шаблоны страницы; сервер подставляет значения из базы. `{{ build.title }}` выводит заголовок сборки.

**CSS**: внешний вид. `.cards` использует `display: grid`; `@media` перестраивает карточки на телефоне.

**Python/FastAPI**: маршруты `@app.get(...)`, `@app.post(...)`, проверка формы, SQL, авторизация.

**SQLite**: реляционная база данных в локальном файле.

## 5. Безопасность

- SQL `?` — параметр; пользовательский текст не становится частью команды SQL.
- Пароль хранится не открытым текстом, а в виде PBKDF2-хеша с солью.
- `request.session` хранит ID вошедшего пользователя в подписанной cookie.
- CSRF-токен проверяется для POST форм.
- `owned_build()` требует совпадения ID сборки и ID владельца.
- Jinja2 экранирует вывод текста в HTML, снижая риск XSS.

**Ограничение прототипа:** он не готов для публичного интернета. Демо-пароли и локальный секрет нужно заменить. Для HTTPS включают secure cookies, проверяют настройку сессий и все формы. Не утверждай, что безопасность уже полностью проверена.

## 6. Что реально работает и что пока отсутствует

Работает: демо-вход, новые сборки, выбор деталей, расчёт цены, редактирование названия, удаление сборки, поиск по каталогу, добавление детали администратором, отчёт для печати и CSV.

Пока отсутствует: автоматическая совместимость, полноценное управление каталогом/категориями, пользовательская регистрация, preference-cookie, дополнительные async/file операции, полный набор тестов и deploy.

## 7. Принцип работы с напарником

Оба участника должны реально работать с кодом и Git. Например, один завершает CRUD сборок, второй — каталог и интерфейс; после этого оба тестируют все сценарии и задают друг другу вопросы. Не приписывай коммиты или знания другого человека себе.
